📌 Project Overview

What is SAFAR?

SAFAR (سفر - Urdu for "Journey") is a peer-to-peer ride-sharing Android application designed specifically for Pakistan. It connects drivers with empty seats to passengers heading in the same direction, creating a community-driven transport solution.

Core Concept

SAFAR enables users to:

  • ✅ Post ride offers (e.g., Lahore → Islamabad at 3:00 PM)
  • ✅ Discover rides via interactive map or searchable list view
  • ✅ Request to join rides with seat selection
  • ✅ Real-time chat with drivers/passengers after approval
  • ✅ Track and manage their posted ads and join requests

Architecture Pattern: MVP (Model-View-Presenter)

Why MVP? SAFAR follows the Model-View-Presenter pattern for strict separation of concerns, making the codebase maintainable, testable, and scalable.

Layer Responsibilities

1. Model Layer (Data Objects)

// Plain Java POJOs (Plain Old Java Objects) // NO Android imports, NO Firebase calls, NO business logic public class User { private String uid; private String name; private String phone; private String profilePicUrl; private float rating; // Getters, setters, constructors only }

Purpose: Pure data containers with no logic. They represent the business entities.

2. View Layer (UI Components)

// Activities and Fragments implement View contracts // ONLY UI updates, NO business logic, NO Firebase calls public class RideDetailActivity implements RideDetailContract.View { @Override public void showRideDetails(Ride ride) { // Update UI with ride data titleText.setText(ride.getOrigin() + " → " + ride.getDestination()); } @Override public void showError(String message) { Toast.makeText(this, message, Toast.LENGTH_SHORT).show(); } }

Purpose: Display data and capture user input. Delegates all logic to Presenter.

3. Presenter Layer (Business Logic)

// Handles ALL business logic and coordinates between View and Repository public class RideDetailPresenter implements RideDetailContract.Presenter { private RideDetailContract.View view; private final RideRepository rideRepo; public RideDetailPresenter(RideDetailContract.View view) { this.view = view; this.rideRepo = new RideRepository(); } @Override public void loadRide(String rideId) { if (view != null) view.showLoading(true); rideRepo.getRide(rideId, ride -> { if (view == null) return; // View destroyed view.showLoading(false); view.showRideDetails(ride); }); } @Override public void onDestroy() { view = null; // Prevent memory leaks } }

Purpose: Contains all business logic, calls Repository for data, updates View via contract.

4. Repository Layer (Data Access)

// ALL Firebase read/write operations happen here // Returns data via callbacks to Presenter public class RideRepository { private final FirebaseFirestore db = FirebaseFirestore.getInstance(); private static final String COLLECTION = "rides"; public void getRide(String rideId, OnRideFetchedListener listener) { db.collection(COLLECTION) .document(rideId) .get() .addOnSuccessListener(snap -> { Ride ride = snap.toObject(Ride.class); listener.onFetched(ride); }); } }

Purpose: Abstracts all Firebase operations. Provides clean data access interface.

Contract Pattern (View-Presenter Communication)

// Contract defines communication interface between View and Presenter public interface RideDetailContract { interface View { void showRideDetails(Ride ride); void showError(String message); void showLoading(boolean show); void navigateToChat(String rideId); } interface Presenter { void loadRide(String rideId); void sendJoinRequest(String rideId, int seats); void onDestroy(); } }

✅ Architecture Benefits:

  • Separation of Concerns: Each layer has a single responsibility
  • Testability: Presenters can be unit tested without Android dependencies
  • Maintainability: Changes in UI don't affect business logic and vice versa
  • Scalability: Easy to add new features without breaking existing code

🔄 Data Flow & Component Interaction

User Action Flow Example: Viewing a Ride

1. User taps on ride pin/card
   │
   ├─► View (MapFragment / ListFragment)
   │   └─► Captures tap event
   │
   ↓
2. View calls Presenter
   │
   ├─► Presenter (AdsPresenter)
   │   ├─► presenter.onRideSelected(rideId)
   │   └─► Validates input, prepares request
   │
   ↓
3. Presenter calls Repository
   │
   ├─► Repository (RideRepository)
   │   ├─► getRide(rideId, callback)
   │   └─► Executes Firebase Firestore query
   │
   ↓
4. Firebase returns data
   │
   ├─► Firebase Firestore
   │   └─► /rides/{rideId} document
   │
   ↓
5. Repository calls callback
   │
   ├─► Callback → Presenter
   │   └─► onRideFetched(ride)
   │
   ↓
6. Presenter updates View
   │
   ├─► View (RideDetailActivity)
   │   ├─► showRideDetails(ride)
   │   └─► UI updated with ride information

Component Communication Patterns

Pattern 1: Activity → Presenter → Repository → Firebase

// Step 1: Activity (View) btnPostRide.setOnClickListener(v -> { presenter.postRide(origin, destination, seats, price, time); }); // Step 2: Presenter (Logic) public void postRide(String origin, String dest, int seats, ...) { if (seats <= 0) { view.showError("Invalid seats"); return; } RideAd ad = new RideAd(origin, dest, seats, ...); firebaseManager.postRideAd(ad, () -> view.showSuccess(), error -> view.showError(error) ); } // Step 3: Repository/Manager (Data Access) public void postRideAd(RideAd ad, OnSuccessListener success, ...) { db.collection("rides") .document(ad.getRideId()) .set(ad) .addOnSuccessListener(success) .addOnFailureListener(failure); }

Pattern 2: Firebase Listener → Repository → Presenter → View

// Real-time updates flow (e.g., chat messages) // Repository sets up listener public void listenForMessages(String rideId, OnMessageListener listener) { dbRef.child("chats").child(rideId).child("messages") .addChildEventListener(new ChildEventListener() { @Override public void onChildAdded(DataSnapshot snap, String prevKey) { ChatMessage msg = snap.getValue(ChatMessage.class); listener.onMessageReceived(msg); } }); } // Presenter handles callback chatRepo.listenForMessages(rideId, message -> { if (view != null) { view.addMessageToChat(message); } }); // View updates UI @Override public void addMessageToChat(ChatMessage message) { messages.add(message); chatAdapter.notifyItemInserted(messages.size() - 1); recyclerView.scrollToPosition(messages.size() - 1); }

Why Realtime DB for chat?
- Real-time synchronization
- Listener-based updates
- Lower latency than Firestore for messaging
- Cost-effective for high-frequency reads/writes

Firebase Operations Examples

Creating a Ride

// FirebaseManager.java public void postRideAd(RideAd ad, OnSuccessListener onSuccess, OnFailureListener onFailure) { db.collection("rides") .document(ad.getRideId()) .set(ad) .addOnSuccessListener(onSuccess) .addOnFailureListener(onFailure); }

Accepting a Join Request (Transaction)

// Ensures atomic seat booking - prevents double-booking public void acceptJoinRequest(String reqId, String rideId, int seats, ...) { db.runTransaction(transaction -> { // Step 1: Get current ride document DocumentSnapshot rideSnap = transaction.get( db.collection("rides").document(rideId) ); int seatsLeft = rideSnap.getLong("seatsLeft").intValue(); // Step 2: Check if enough seats available if (seatsLeft < seats) { throw new FirebaseFirestoreException( "Not enough seats", FirebaseFirestoreException.Code.ABORTED ); } // Step 3: Update seats (atomic) transaction.update( db.collection("rides").document(rideId), "seatsLeft", seatsLeft - seats ); // Step 4: Update request status transaction.update( db.collection("requests").document(reqId), "status", "ACCEPTED" ); return null; }); }

// ChatRepository.java - Firebase Realtime Database public void listenForMessages(String rideId, OnMessageListener listener) { DatabaseReference messagesRef = FirebaseDatabase.getInstance() .getReference("chats") .child(rideId) .child("messages"); messagesRef.addChildEventListener(new ChildEventListener() { @Override public void onChildAdded(DataSnapshot snapshot, String previousChildName) { ChatMessage message = snapshot.getValue(ChatMessage.class); listener.onMessageReceived(message); } // Other lifecycle methods... }); }

⚙️ Development Setup Guide

Prerequisites

  • ✅ Android Studio (Latest version - Hedgehog or newer)
  • ✅ JDK 11 or higher
  • ✅ Android SDK with compileSdk 35
  • ✅ Firebase Project (create at Firebase Console)
  • ✅ Google Maps API Key

Step 1: Clone the Repository

git clone <repository-url> cd "SAFAR ktjava"

Step 2: Firebase Configuration

📋 Firebase Setup Checklist:

  1. Create a Firebase project at console.firebase.google.com
  2. Add an Android app with package name: com.safar.app
  3. Download google-services.json
  4. Place it in app/ directory
  5. Enable the following services:
    • Authentication → Phone
    • Authentication → Google
    • Firestore Database
    • Realtime Database
    • Cloud Messaging (FCM)
    • Storage

Step 3: Google Maps API Key

  1. Go to Google Cloud Console
  2. Enable Maps SDK for Android
  3. Create an API key
  4. Add key to local.properties:
MAPS_API_KEY=your_api_key_here

Or add directly to AndroidManifest.xml:

<meta-data android:name="com.google.android.geo.API_KEY" android:value="YOUR_API_KEY_HERE" />

Step 4: Build and Run

  1. Open project in Android Studio
  2. Sync Gradle files
  3. Connect Android device or start emulator
  4. Click Run ▶️

Common Issues & Solutions

⚠️ Issue: "google-services.json not found"

Solution: Ensure google-services.json is in the app/ directory (same level as app/build.gradle)

⚠️ Issue: "Map not showing"

Solution: Check if Maps API key is correctly configured. Enable Maps SDK in Google Cloud Console.

⚠️ Issue: "OTP not receiving"

Solution: Add SHA-1 fingerprint to Firebase project settings. For debug builds, use debug keystore SHA-1.

🎓 Summary & Best Practices

Key Architectural Principles

  1. Separation of Concerns: Models, Views, Presenters, Repositories - each has ONE job
  2. Contract Pattern: All View-Presenter communication through interfaces
  3. Null Safety: Always check if view != null in Presenters before calling view methods
  4. Memory Management: Call presenter.onDestroy() and set view = null in Activity/Fragment onDestroy()
  5. Language Consistency: Java for logic, Java/Kotlin for UI (match existing files)
  6. Firebase Abstraction: All Firebase calls in Repositories/Managers, never in Activities

Development Workflow

  1. Define data models in models/
  2. Create Contract interface in views/contracts/
  3. Implement Presenter with business logic
  4. Build Repository for data access
  5. Create Activity/Fragment implementing View contract
  6. Test with Firebase in development environment
  7. Deploy Firebase security rules
